## Remaining limits

Authentication-denial audit events and session idle-timeout behavior remain review findings; absolute expiry already exists. Whole-system resistance to distributed denial of service, recovery procedures, live deployment transport policy and user acceptance are not established here. The local blocklist is finite and is not a live breach database. Legacy accounts upgrade on successful login rather than being forcibly reset. Multi-process resource budgets require explicit deployment tuning. File fsync regression uses controlled injected failures; Linux directory fsync is code-reviewed here and should be exercised by the container integration run. Human service-purpose achievement and measured real tourist revisit effects cannot be inferred from these code checks.

Reference: [OWASP Password Storage Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html), fixed scrypt profile N=2^15, r=8, p=3. ## Independent account-module review (read-only follow-up)

A reviewer other than the account-module author inspected `account/router.py`, `account/schemas.py`, `account/service.py`, `password_policy.py`, the local list provenance/packaging and `test/backend/test_account_security.py`. No additional application edits or test runs were performed during this follow-up, avoiding overlap with the parent's integration run. No actionable defect with a demonstrated harmful path was found in this inspected scope.

- **Actor and confirmation:** The route obtains the account ID exclusively from the authenticated session. Extra actor IDs are rejected by the request schema. The existing authentication dependency enforces CSRF for this write; an invalid explicit bearer cannot fall back to a different cookie. Current-password verification precedes any change. Password values use SecretStr request fields and are never included in success/error responses.
- **Concurrency and atomicity:** Both KDF operations execute outside a DB transaction. The serialized write transaction rechecks token/user binding, absolute expiry, enabled state, username, salt, password hash and CSRF snapshot. Logout, disabling or a competing password change can therefore defeat the attempted update. New hash/salt and both cookie/Stage session-table deletions commit together. The reviewed tests include revocation-trigger failure rollback. Concurrent legacy auto-upgrade may cause a safe retry instead of an unsafe overwrite.
- **Session boundaries:** A successful change revokes all sessions for that user in both tables and preserves unrelated users. Cookie-initiated requests clear the cookie. Stage-initiated requests leave an unrelated cookie untouched while their bearer is invalidated. Clients must honor reauthentication_required; the API does not issue a replacement session implicitly.
- **Weak-password screening:** Registration and password change use the same bounded 12–128-character policy; existing login/seed credentials are not retroactively blocked. Screening case-folds only a comparison copy. Stored/authenticated passwords retain their exact string. The fixed 46,825-entry SHA-256 set is checked for file digest, shape and count at import; contextual account/site-name checks supplement it. The historical source/version, transformation and MIT license are recorded locally. This is finite common-password coverage, not a complete breach check or a claim that every predictable variation is rejected.
- **Local delivery and failure privacy:** The blocklist is a bundled file; no runtime network lookup is introduced. Docker copies backend/app and explicitly re-includes password_policy.py after its general secret-name exclusion; the list's filename remains included. Static responses resolve inside the separate frontend static root, with path containment and dot-path checks. Validation errors are replaced with a generic response, and exception logs include exception class only. The shared Unicode guard rejects malformed scalar strings before encoding. Docker startup is still the parent's integration responsibility, not evidence created by this read-only review.

Limits remain unchanged: no new authentication-denial audit trail or idle-session timeout, no exhaustive breach intelligence, no proof about external deployment TLS, and no claim that all concurrently in-flight application operations are cancelled at the instant sessions are revoked. These are separate system-level acceptance questions.
