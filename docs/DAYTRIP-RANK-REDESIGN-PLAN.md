# 日帰り中距離・先達・ランク特典・和の画面への改訂計画

作成：2026年11月10日（日本時間）。計画版 P2。CP52〜63。最新音声指定で距離を20〜40kmへ変更。

最初の依頼は「大幅な修正に向け、まずタスクを精査」。その後、同日音声チャットで利用者が本チャットの作業を「複数エージェントで実装してください」と明示したため、計画保存に続いて実装・統合・検証へ進む。新しい機能の完了は個別の証拠で判断する。DESIGN.mdの追加仕様として参照し、作業状態はTASKS.mdとローカルチケットで管理する。

### 現在の採用設定

**ターゲティングゾーン：選んだ出発拠点から、主目的地まで片道20〜40km。宿泊なし・同日帰着。**

- 距離は交通手段に応じた経路距離。直線距離の円を描いて道路距離と称しない。集合駅・公共の集合場所などを起点にし、自宅住所の登録は必須にしない。
- 行き先探索では本人の選んだ発地、講で共有するときは合意した集合地点に基づいて再判定する。個人ごとの自宅から集合場所までの負担は別の情報である。
- 各参加者は集合地点までを含む移動負担が自分の希望内か確認する。全員の平均だけで「気軽」と判定せず、不明な人は未確認のまま表示する。自宅位置は収集しない。
- 20km未満は範囲より近い場所、40km超は範囲外と分類する。ターゲティングゾーンは優先する市場の範囲であり、それ以外の利用禁止や保存済み旅行の削除ではない。
- 旧50〜100kmは初版の主ゾーンへ含めない。初期経路を町田・新百合ヶ丘へ切り替え、小田原/箱根のみが出る状態を避ける。遠距離を選ぶだけで特典を大幅に増やさない。
- 鉄道・自動車の経路/参考所要時間、確認日、情報源、算定方式を同梱する。運行や渋滞のライブ情報ではない。乗換え/アクセスを含めた時間が未確認なら「要確認」とし、自動でゾーン適合としない。
- 登録された現地滞在と帰着の行程から、一日で無理なく使える時間が残るかを確認する。初期目標は現地4時間程度を確保すること。これは調査の実測値ではなく製品の行程設計目標。
- 既存の架空都市や県の代表座標から実移動距離を捏造しない。初版は発地と目的地を限定した、根拠を確認できる経路カタログから始める。

### 既存500人データとの関係

[既存分析](SAMPLE-DATA-TRENDS.md)では、居住地域ラベルと実在地域の対応が未確認。講の開催ID、実参加、本人の出発拠点、経路距離も揃っていない。したがって、500人から20〜40kmが最適と導いたり、過去ポイントを自動付与したりしない。

異なる日付のスタンプが複数ある人も別旅行/実再訪とは断定できず、スタンプ数を講の実施回数へ転記しない。今回の距離・先達・割引効果は新たに測定する項目である。

## 3. 実施回数・先達・ポイント・割引

### 先に追加する記録

継続する仲間の単位である「講」と、日付のある「今回の開催」を分ける。同じ講で同じ地域へ再び出かける回を作れるようにする。

現在の見積の双方確認は予約や実施の証拠ではない。既存の振り返りには旅行終了/利用の申告があるが、講×事業者に対して一件で、反復開催の実績台帳には不足する。写真位置や訪問バッジも本人の記録であり、そのまま割引原資に関わる実績へ変換しない。

開催は「計画中→開催予定→実施申告→確認済み」、別に「中止・訂正・確認待ち」を区別する。開催回ID、日時、行程版、実参加者、先達、確認した人と時刻を保存する。

### 先達の扱い

- 先達はその開催の募集・日程調整・取りまとめ等を担う人。利用ランクとは別の役割であり、上級ランクの名称に流用しない。
- 初版は一開催一人。本人の承諾と他の参加者の確認を記録し、作成者というだけで自動認定しない。交代の履歴を残し、追加点の対象者を確定する。
- 実施前の先達交代は可能。開催後の追加点の付け替えには訂正処理を用いる。欠席者、名義だけの先達、チャット発言が多いだけの人を自動加点しない。
- 参加者は役割を引き受けなくても基本点と距離点を獲得する。先達を強制せず、能力/人格の優劣の順位表を作らない。

### 数値のたたき台（未採用・制度試算用）

個人の獲得点を次のように構成する案をまず比較する。

`開催の参加100点 + 行程距離10kmあたり1点（最大20点） + 先達50点`

ここで行程距離は、合意して保存した集合地点〜目的地〜帰着の往復参考経路。無関係な寄り道・自宅からの移動・GPSの細分化は含めず、本人が全行程へ参加した確認に対応させる。部分参加は参加点のみとし、距離不明のときも0点と未確認理由を明示する。これは実測GPS距離ではない。

例：片道30.8km、往復61.6kmの開催では参加者106点、先達156点（10km単位未満を切り捨て）。基礎の100点が反復開催を評価し、距離の影響を20点以内に抑える。数値は需要データで最適化されたものではなく、先達の負担と不正のしやすさを比較する初期案。

利用ランクは個人の累積有効ポイントで判定する。初期比較案は0・300・800・1,500点の4段階。名称は仮に一段〜四段とし、最終的には読んで理解できる表示で選ぶ。ポイントは資格判定用で、現金化・購入・他人への譲渡・ポイント払いは今回含めない。初版で毎年の失効は設けず、取消があれば有効残高とランクを再計算する案とする。

### 不正・訂正・整合性

- 加点は確認済みの開催への実参加について一度だけ。提案、候補保存、講作成、写真追加、見積確認だけでは付けない。
- 初版の確認案は本人の参加申告＋先達以外の参加者による実施確認。事業者利用がある開催では、受入事業者の利用確認も別に保持する。これはアプリ上の確認記録で、外部の真の現地訪問を完全に証明するものではない。
- 事業者なし開催の確認強度と特典資格はCP55/58で決める。自己申告だけの開催を金銭的割引の資格へ自動昇格させない。
- 同じ本人・開催回・加点種別は一意。同一行程の分割登録、日付重複、取消再作成、先達名義の交代で点数を増やせない受入条件を置く。初期案は一人一日一開催を加点上限とする。
- 付与/取消/訂正を追記型の台帳へ残し、元の記録と計算規則の版を保持する。同時操作、再送、再起動でも二重加点しない。
- 同じ地域へ別日に再訪した実施回にも基本点を付ける。新規地域の開拓だけを優遇しない。連続記録の途切れによる罰は設けない。

### 割引は事業者が条件を設定して成立させる

ランクに応じて利用できる特典を、対象事業者・対象プラン・期間・適用ランク・率/額・上限額・人数単位・併用可否・負担者とともに登録する。ランク表示だけで全事業者の価格を勝手に下げない。

- 初期案は事業者負担の任意参加型。プラットフォーム負担や共同負担は別の設定・予算が必要。
- 3%/5%/7%等はCP58で採算を比較する仮定に限り、本計画では提供を約束しない。料金範囲に対する曖昧な値引きを避け、合意した対象額と円単位の端数処理を定める。
- 適用資格は各人のランクを用い、初期案では各人の対象料金へ適用。一人の先達のランクを無断で講全員へ適用しない。団体一括料金の場合は別の適用条件を事業者が明示する。
- 見積に通常額・割引額・割引後額・適用条件・規則版を残す。割引の確保、事業者の利用確定、取消/戻しを分け、同じ特典の同時二重利用を防ぐ。
- ポイント訂正でランクが変わった場合、未利用特典は再判定する。利用済み金額を自動改変せず、事業者が確認する調整記録へつなぐ。外部決済は接続せず「入金済み」を捏造しない。
- 同地域の次回利用で使える特典を事業者が設定できるようにし、再訪へつなぐ。ただし期限や割引だけで再訪効果があるとは断定しない。

## 4. 重すぎない和の世界観

富士講の人々を迎えた御師の家、先達、旅の道具や印の文化を調べ、共同で出かける関係と記録の意匠へ取り入れる。[国土交通省の御師住宅解説](https://www.mlit.go.jp/tagengo-db/R1-00152.html)、[富士吉田の公式紹介](https://www.fujiyoshida.net/feature/index.php?p=fujikoplan)を参照。歴史的な先達の宗教上の資格と、本アプリの旅行を取りまとめる役割を同一視しない。

| Before | After | Why |
|---|---|---|
| Airbnbを主な視覚基準にしたカード一覧 | 明るい生成りの面、墨色の文字、控えめな朱色、細い罫線、写真の大小がある一覧 | 選びやすさを残し、講の旅の記録としてまとまりを出す |
| すべて同じ丸み・同じ大きさのカードへ寄りがちな構成 | メインの旅、日程一覧、手帳の実績、割引の札で形と情報量を変える | 画面の役割と優先順位が分かる |
| アプリ共通の均質な見出し | 短い見出しだけに読みやすい明朝、本文・価格・日時・入力はゴシック | 和の雰囲気と日常的な操作性を両立する |
| 数字のポイント/ランクを足すだけ | 旅の手帳に実施回数・行程距離・先達回数・獲得理由、控えめな印と進捗 | 実績と次に使える特典の関係を説明できる |
| 派手な達成演出・繰返す動き | 加点確定時だけ短い印の表示。操作は即応、静止時は動かさない | 重厚感やPC負荷を増やさず意味を伝える |

方向性は明るい余白7割程度を保った「旅の手帳と地域の案内」。濃い木目、全面の古紙、金箔、筆文字の長文、縦書きフォームなどは主画面に持ち込まず、写真と内容を読む場所を確保する。配色比率は見本比較用の目安である。

ログイン・日帰り一覧・講の会話・手帳/ランク・事業者の特典設定・左右2台を同じ設計規則で整える。先達は初出時に「先達（取りまとめ役）」と補い、意味のない雅語や詩的なコピーへ置き換えない。字体や画像はローカル同梱、ライセンス確認と容量調整を行う。

計画整理として完了するのはCP52。続く音声承認に基づきCP53〜62の実装・統合・検証を開始する。CP63は文書と版の対応を更新し、紹介動画は変更後の実操作確認後に更新する。割引はローカルに登録された事業者の明示操作で公開し、外部契約・実決済を新たに発生させない。

### 実装時の順序

1. CP53（距離カタログ）、CP55（開催の実績）、CP59（和の見本）を独立して進める。
2. 開催モデルに先達を接続してCP56、距離/実施とつないでCP57。別担当でCP54の探索を整える。
3. CP58の特典条件と計算を固め、CP60で旅行者と事業者の往復へ統合する。
4. CP61/62で計算・保存・使いやすさ・負担を確認し、結果をCP63へ反映する。

最初に通す操作は「片道30.8kmの日帰り候補を講に追加→先達を決める→開催/参加を確認→参加者106点・先達156点の内訳→次の開催で条件に合う特典を選ぶ」（点数は上記案の場合）。別の検証で中止・未参加・重複送信・先達交代・割引取消を通す。技術試験と実際の地域再訪の測定を混同しない。

## 7. 評価の追加範囲

- 計算：付与/取消/再計算の期待値、距離とランクの境界、同時処理の一意性。全対象シナリオを表にして通過/未通過を記録。
- 安全性・保存：本人/先達/事業者の権限分離、共有先確認、履歴の追跡、移行/再起動/隔離復元。アプリ上の確認を現地訪問の完全な証明としない。
- 使いやすさ：320/390pxと1440×900二台、200%文字、キーボード、焦点、コントラスト、動きを減らす設定。伝統的な見た目を理由に操作性を下げない。
- 負担と継続：先達になる人の偏り、先達の作業時間/負担感、参加者の理解、距離ごとの到達ランク、特典額/実施回。想定データによる試算と実利用調査を区別する。
- 再訪：同じ地域への次回の候補保存、日程確定、確認済み実施を分ける。30/60/90日の追跡では観測期間が足りる人だけを分母にする。再訪率向上の因果をUIやポイント導入だけで主張しない。
- 既存評価：C1/Q1の以前の値・範囲を保持し、今回の受入結果を別版で追加。設計書や起票だけで実装点を加点しない。
