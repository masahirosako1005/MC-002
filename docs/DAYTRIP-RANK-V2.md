# 日帰り・旅の階級 R2

2026-11-10。利用者指定の番付順をアプリ内の旅の階級として採用する。宗教上の資格・認証を示すものではない。開催ごとに任命・承諾する「開催の先達」は、旅の階級「先達」と別の役割である。

## 階級と維持条件

|番号|旅の階級|有効累積点|上位の維持に必要な直近365日活動点|
|---:|---|---:|---:|
|1|新客|0|なし|
|2|行者|100|なし|
|3|山伏|300|なし|
|4|先達|800|なし|
|5|大先達|1,500|1,500|
|6|正大先達|2,500|2,500|
|7|前鬼・後鬼|4,000|4,000|
|8|別当|6,000|6,000|
|9|大僧正|9,000|9,000|
|10|勧進元|13,000|13,000|

閾値は今回のアプリ運用案。先達役割を含む1回約150点の活動なら、大先達は年10回程度から維持できる水準とした。加点規則D1（参加100＋往復参考距離点＋開催の先達50）と、同一人1日1開催上限は変更しない。

現在の階級は、累積点で保証される下位4階級と、累積・直近活動点の両方を満たす上位階級のうち高い方。時間経過だけでは累積点も台帳も削除しない。取消は既存の追記取消台帳で有効点を訂正するため、累積保証も訂正後の有効点に基づく。無活動の高位者は、下位の累積保証まで下がる。

活動日は開催終了日時。判定時刻をTとし、`T-365日 < 終了日時 <= T` の開催ごとに全加点・取消を相殺してから合算する。確認・事業者承認が遅れても365日の起点は延長しない。古い開催の取消を「今日の活動のマイナス」として扱わない。時刻はUTCで比較し、画面では日本時間で表示する。端末時刻は判定に使わない。

## API契約

既存URL・認証・権限を維持する。`GET /api/daytrip/catalog` のrulesは加点version=D1のまま、`rank_policy_version: "R2"`、`rank_window_days:365`、`rank_lifetime_floor_max:4`、`rank_names`、新`rank_thresholds`を返す。

`GET /api/daytrip/me` は従来の `points`, `eligible_points`, `rank`, `eligible_rank`, `next_rank_points`, 開催件数・台帳・特典・確保済み特典を保持する。rankは1〜10。以下を追加する。

```ts
type RankStatus = {
  policy_version: "R2";
  rank: number;
  name: string;
  lifetime_points: number;
  recent_points: number;
  lifetime_rank: number; // 累積点だけなら到達する階級。過去の最高階級ではない
  guaranteed_rank: number; // 有効累積点で保証される下位1〜4
  maintenance_points: number | null; // 上位の維持に必要な直近点
  next_rank: number | null;
  next_rank_points: number | null; // 次階級の閾値総点
  next_lifetime_points_needed: number;
  next_recent_points_needed: number;
  next_demotion_at: string | null; // 活動・取消が追加されない場合の次の降格時刻
  evaluated_at: string;
};
// me.rank_status: RankStatus
// me.eligible_rank_status: RankStatus
```

表示階級は全有効点、特典対象階級は事業者が確認した有効点で同じR2を適用する。自己申告・仲間確認だけの点は金銭特典の資格に使わない。加点・取消・判定は同じSQLiteトランザクション内の状態から計算する。

`POST /api/daytrip/benefits` は新画面から `rank_policy_version:"R2"` を送り、min_rankを1〜10で指定する。版を省略した旧クライアントはD1の1〜4として解釈し、新1/3/4/5へ変換して保存する（旧四段1500点を新先達800点へ誤って緩めない）。D1で5以上を送ると422。特典出力のmin_rankはR2番号へ統一し、`rank_policy_version:"R2"` と `original_rank_policy:"D1"|"R2"` を付ける。既存特典は旧1/2/3/4を新1/3/4/5へ変換し、元の0/300/800/1500点の条件を不用意に緩めない。新特典は既存settingsへ `daytrip-benefit-rank:<benefit_id> = R2` を同一トランザクションで記録する。既存特典・ユーザー・台帳・画像・schema番号は書き換えない。

## 割引の確保と降格

新しい確保では、その開催自身の点を除外した現在の特典対象階級を使う。確保時の階級・有効累積点・直近点・R2を既存conditions_jsonへ保存する。さらに `rank_evidence` に開催ごとの終了日時、有効資格点、その時点の資格台帳ID集合を保存する。APIは内部の根拠ID一覧を共有画面へ返さない。

確保後に365日の窓から活動が外れて降格しても、確保の取消や料金の再計算をしない。利用時は確保時の階級条件を引き継ぐ。本人の実参加、事業者確認、利用期限、対象プラン版、所属、事業者権限、同時二重利用の検査は継続する。従来の確保済み特典も保存済み金額を維持する。

事実訂正による過去の点の取消は、自然な期間経過と区別する。R2の訂正判定では確保時の日時・根拠だけを再評価し、保存後に追加されたマイナスだけを反映する。後の新規活動や、同じ開催への再承認によるプラスは資格根拠を補填しない。無関係な古い開催の訂正や自然降格そのものでは確保を変えない。

旧D1の確保には根拠ID集合がないため、確保のcreated_at以前の台帳と、それ以後の取消だけを開催単位で相殺し、旧来の累積資格条件で判定する。確保後の正点は用いず、R2の年間維持条件を遡って課さない。旧行や旧conditions_jsonは移行時に書き換えない。

資格根拠を取り消して確保時条件を満たさなくなった未利用特典は取消対象となるが、保存済み金額は書き換えない。利用済み金額は保持し、実際にその資格根拠へ影響したときだけ調整要否を記録する。開催自体の中止、参加取消、事業者による特典終了・参加権限失効も従来どおり扱う。
