## 設計と調査の対応

| 観点 | 判断 | 留意点 |
|---|---|---|
| 場所ごとの標本と段階 | 調査からの設計案と整合 | 独自の図案・名称で実装し、既存サービスの画像やAPIを使わない |
| 12種類・3セット | 固定の小さな分母を持つ設計として妥当 | この件数が最も面白いという実測根拠はない |
| 次の目標の保存 | 行動を選ぶ機能として整合 | 選択・予定保存を獲得や訪問の証拠にしない |
| 別日の訪問 | サーバーの記録で判定する契約 | 連泊中の翌日も含む。現地コードの共有を排除できず、実際の別旅行による再訪を証明しない |
| 会議館から続く旅 | 会議館の初訪問より後の別日に他地点を訪れる条件 | 会議への出席や、その会議が再訪を引き起こした因果関係までは分からない |
| 時期と難易度の枝 | 異なる行動に向かう設計として整合 | 上級課題の達成を別日再訪へ加算しない。季節待ちは今日可能な行動と区別する |
| 獲得と完成 | 実装で表示が分離され、初回の懸念を解消 | summary.earnedは「獲得した記念品」、sets.earnedは「最後まで集めた記念品」。段階表示には「獲得・続きあり」と「完成」がある |
| 長期の称号 | 任意の目標として採用可能 | 続く旅セットは複数日・複数季節が必要。1枚・1段階でも達成を認め、長期完成まで初回の喜びを先送りしない |

上記は設計上の判断であり、面白さ・利用者満足度・再訪意欲の実証ではない。

## 残る限界と別担当の確認

- 独立レビュー自身が実行したのはコード読取りとローカルAPI・純粋判定の確認。後述するブラウザー等の保存結果照合とは区別する。スマホ実機・読み上げ・全操作状態・実利用者評価は未検証。
- 印刷コードの共有と同一旅行中の翌日訪問を排除できない。別日記録の増加を、そのまま実旅行の再訪率や施策の効果として扱わない。
- 四季と長期称号には時間が必要。最初のひと組・段階獲得で早期達成を用意したが、楽しさ・飽きにくさ・継続意欲は利用者テストが必要。
- 導出履歴の日時はサーバーがJSTで保存した形式を前提とする。OS管理者によるDB改変や未検証の外部履歴インポートは保証範囲外。
- 判定定義のバージョンは1。将来閾値や既存IDの意味を変更すると、過去の収集結果も再計算で変わり得るため、定義版と移行方針を先に定める。
