## 体験上の不足

1. `App.tsx` のpage/communityId/circleTarget、`PlanDiscovery.tsx` の選択講・検索・絞り込みはReactのstateで、再読み込み時に本人の作業位置へ戻れない。保存した講そのものはDBにあるが「どれを開いていたか」は保存されない。
2. ホームから本人の確認済み関心と適用先がすぐ分からず、同じ初期設定の3人では個人化の違いが見えにくい。説明を長くするより、本人の関心チップと「好みを見直す」、現在選んだ講と「続きから開く」を実データで示すのが小さい改善となる。
3. ログイン可能な初期アカウントと本人プロフィールは存在するが、自分の新規アカウント作成/パスワード変更の画面は現在の対象コードにはない。個人の長期利用へ広げる場合の別要件であり、今回の再開機能と混ぜて実装済みとはしない。

## 最小追加案：本人用の再開状態（未実装の契約案）

DBが保存済み内容の正本となる。ブラウザーの共有localStorageを正本にせず、Cookie/sessionや左右の画面の認証モデルを変更しない。これは操作位置の保存であり、行動履歴収集・未送信チャット保存・予約・参加承諾ではない。

### API

`GET /api/me/resume-state` と `PUT /api/me/resume-state`。どちらも既存認証必須、PUTは既存CSRF/Origin検査を使用する。user_idをURL/本文から指定させない。レスポンスは本人だけが見られ、他者profile、公開bootstrap、事業者招待snapshotには出さない。

| フィールド | 型・制約 | 意味 |
|---|---|---|
| version | 0以上の整数、GETで返しPUTで必須 | 未保存は0。更新は比較交換、古い版は409 |
| page | `feed` / `market` / `circles` / `journal` / `provider` | 現capabilityで利用可能な画面だけ。内部ページ名との対応はfrontendで固定 |
| community_id | null または既存ID | 本人の現active所属のみ |
| circle_id | null または既存ID | 本人が承諾済みで参加中、同じcommunity、openの講のみ。pending招待では保存/復元不可 |
| filters.query | 最大120文字、空文字可 | 公開候補の本人用検索。共有しない |
| filters.category | 空文字または許可済みタグID | 公開カタログの絞り込み |
| filters.duration | `all` / `day` / `overnight` | 現UIの3択 |
| filters.schedule | `all` / `dated` / `on_request` | 現UIの3択 |
| filters.area | 最大100文字、空文字可 | 現公開カタログから選んだエリア。候補不足と権限喪失を混同しない |

PUTは全状態を保存し、未知フィールドを拒否する。存在しないID/他者専用IDは同じ404として存在を漏らさない。circleを指定した場合のcommunity不一致は拒否し、クライアント入力から所属を作らない。通常の検索で0件になっただけなら本人が選んだfiltersを残し「解除」できる。

新規schemaは1テーブル `user_resume_state`（user_id PRIMARY KEY/FK、page、community_id、circle_id、filters_json、version）。保存日時は表示要件がなければ追加しない。既存schema 7の全表/全行を保全する追加移行とし、seedの関心・許可・会話を変更しない。

### 無効化と再開

- ログイン成功後、本人のデータと再開状態を取得してから初回表示を決める。読み込み途中に前のユーザーの内容を出さない。未保存は現在の既定画面と初期値に戻る。
- コミュニティ退出、講メンバー除外、講close/deleteで参照を無効化する。参照先だけを消し、本人の関心や講の本体を削除しない。community喪失時はcircleとfiltersも既定値へ戻す。
- 退出して再加入しても旧状態を無断復活させない。membership削除/失効とcloseの同一transactionで状態をclearするtrigger/サービス処理を置き、GETでも現権限を再検査する。古いschema/直接変更から不正参照が残っていた場合は清掃し、その版を返す。UIだけの非表示では不十分。
- provider権限を失った場合はprovider画面を復元せず安全な既定画面へ。ホームに事業者の非公開planや相談が紛れ込まない。
- 状態保存は明示的な画面/講/条件選択に合わせて行う。検索文字は短いdebounceで保存し、古い応答が後の選択を巻き戻さない。保存失敗時に現在画面は使えるが、保存成功と偽表示しない。
- 409は最新状態を取り直して調停する。古い別タブの全状態を無条件で再送して、もう一方の新しい選択を上書きしない。
- ログアウト/アカウント切替では保留timer・request結果を破棄し、userとgenerationの両方を照合する。左右の別認証を維持。同一ユーザーを二箇所で使うときだけ共有する本人状態となる。

### ホームの最小表示

本人の確定関心チップと「好みを見直す」、選択中コミュニティでの利用許可の状態、現権限で開ける講の「続きから開く」を示す。関心未登録/許可OFFは率直に示し、勝手にONにしない。会話本文・他人の関心・記念日名をホームの共有領域へ複製しない。候補や行程の本体は既存APIから最新状態を取得する。

## 意味のある受入試験案（未実施）

1. 隔離DBのA/Bが異なる本人関心を明示保存し、同一公開カタログ/同一communityで順位またはscoreが変わる。Bの編集でAの結果は変わらない。Aの利用許可OFFで本人加点が消える。既存 `test_discovery.py` の該当試験を再利用し、実DBのseedを書換えない。
2. A/Bが別の再開状態を保存し、新しいDB接続/新しいapp lifecycle後にも本人の値だけを読む。公開bootstrapと他者profileには状態が出ない。未認証は401、他人ID/招待pendingは404。
3. 同じ版から2リクエストを競合させ、片方成功・片方409。遅い応答、ログアウト直後応答、A→B切替直後応答でBの画面/状態が汚れない。
4. 講退出/コミュニティ退出/close後に再開先が消え、再参加だけでは復活しない。GET前に退出→再参加が完結する場合も検証する。
5. schema 7の非空DBを移行し全既存行を比較、migration failureはrollback、二回適用可能。稼働volumeの検証は動画終了後に主担当が直列で実施する。
6. Docker画面で本人の関心/許可を見直す→候補の理由が変わる→講/絞り込み選択→再読み込み→再ログインで復元。別アカウントでは別状態。候補保存が招待/予約へ変わらないことも回帰確認する。
