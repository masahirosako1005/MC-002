## 2. 発見事項

### SEC-01 — 年境界で過去の謎達成が未達成表示へ戻る

- **重大度:** 中（業務・表示整合性）。認証突破やDB消失ではない。
- **状態:** 修正確認済み。
- **箇所:** [Journal.tsx:36](../frontend/src/Journal.tsx)、[service.py:63](../backend/app/service.py)、[test_api.py](../backend/tests/test_api.py) の `test_completed_attempt_keeps_season_when_catalog_moves_to_next_year`。
- **原因:** 修正前は完了したattemptの `game_id` を現在の `catalog.games` に照合して季節を算出していた。カタログは年度で絞られるため、翌年に古いゲームを照合できない。
- **再現:** 2026-11-09に秋の謎を完了し、2027-01-03に時計を進めた。完了attemptは前後とも1件だが、表示用照合の成功件数は0件となった。
- **影響:** 再訪して収集を振り返る利用者に、獲得した季節が「これから」と表示される。
- **修正:** journalのattemptに対応ゲームの `season` を返し、フロントは保存済みattemptの季節で収集表示を組み立てる。旧年度ゲームを現行カタログへ混入させる必要はない。
- **確認:** 翌年への移行、復旧後もattempt内容が保持される追加API試験に合格。フロントが現在カタログを参照せず `a.season` を用いることをコードで確認。
- **追補確認:** 主担当のブラウザー試験「過年度の謎の季節がカタログに依存せず残る」が合格。journal APIを過年度の完了attemptで差し替え、現在カタログに存在しないゲームでも秋の収集印が1件表示されることを確認する試験である。実時計を進めたフルスタックE2Eではなく、上記API年境界試験と組み合わせた検証。証拠: [journey.spec.ts](../qa/tests/journey.spec.ts)、[browser-tests.json](../artifacts/browser-tests.json)。

### SEC-02 — 想定外500応答が共通セキュリティヘッダーを通らない

- **重大度:** 低（防御の一貫性）。汎用JSON本文に秘密や入力値は含まれず、XSS成立は確認していない。
- **状態:** 修正確認済み。
- **箇所:** [main.py:63](../backend/app/main.py)、[security.py:34](../backend/app/security.py)。
- **原因:** 例外ハンドラーによる最外層の500応答が通常ミドルウェアの `secure_send` を通らず、CSP・no-storeなどが欠落した。
- **再現:** `JourneyService.journal` に `RuntimeError` を注入。修正前は500かつ汎用本文だが、CSPとCache-Controlがともに未設定だった。
- **修正:** 共通の `response_security_headers()` を定義し、想定外例外のJSON応答にも適用。
- **確認:** 同じ例外注入を独立再実行し、500・秘密非露出・`Cache-Control: no-store`・`base-uri 'none'` を含むCSPを確認。

### SEC-03 — 成功済みセッション初期化Promiseが失効後も残る

- **重大度:** 低（復旧操作・保守性）。サーバー側認証は拒否するため、権限突破ではない。
- **状態:** 修正確認済み。Promiseキャッシュ、通常書込み後の401/CSRF失効、復旧ダイアログを先に使う追加経路まで、下記の試験範囲で確認した。
- **箇所:** [api.ts:23](../frontend/src/api.ts)、[api.ts:49](../frontend/src/api.ts)、[api.ts:85](../frontend/src/api.ts)、[App.tsx:43](../frontend/src/App.tsx)、[security.py:59](../backend/app/security.py)、[Recovery.tsx:15](../frontend/src/Recovery.tsx)、[Recovery.tsx:92](../frontend/src/Recovery.tsx)。
- **修正前の根拠:** `sessionPromise` は成功後に解放されず、初期化処理自身が失敗した場合だけnullになっていた。他のAPIの401/403では更新されなかった。
- **修正前の影響:** ページを開いたままのセッション失効や、別タブの復旧で認証状態が変わった後、画面内再試行だけでは初期化がやり直されない場合があった。全画面再読込で回避できた。
- **修正:** `openSession().finally(...)` で成功・失敗双方の終了後にnullに戻し、同時実行だけを共有する。`recover()` 後もnullに戻す。変更APIの無条件自動再送は追加していない。
- **確認:** 主担当の「初期読込の再試行でセッション情報も再取得する」が合格。初回journalを503にし、再試行後の画面復旧とGET `/api/session` が2回以上であることを検証する。別ブラウザーの復旧後に保存済み候補が表示される試験も合格。証拠: [api.ts:78](../frontend/src/api.ts)、[journey.spec.ts](../qa/tests/journey.spec.ts)、[browser-tests.json](../artifacts/browser-tests.json)。
- **追加修正:** `sessionOpened` がtrueのページでは、GET sessionの401後に匿名手帳を自動作成しない。通常APIの401またはCSRF専用 `X-Session-Invalid` 応答は全体エラーへ通知し、手帳・開いていた謎・通知を画面状態から消して再読込を案内する。通常の業務403を一律にセッション失効扱いにはしない。変更APIは再送せず、利用者の再操作を必要とする。
- **追加確認（主担当実行の試験を独立照合）:** 別ブラウザーで実際に復旧して旧セッションを失効させ、元画面の保存失敗→画面内再試行→合言葉で復旧を通し、候補が同じ1件であることを確認。元画面の保存POSTは1回のままで、拒否された保存の自動再送はない。同一ブラウザーの別タブではCookieのみ更新され旧タブのCSRFが古くなる状況を作り、403＋専用ヘッダー→画面内再試行→候補1件保持→明示的保存で同じ手帳に2件となる。失敗から再試行まで匿名手帳作成POSTは0回。別タブを再読込して同じ2件を確認する。
- **追加指摘の履歴（低・復帰UX）:** 中間版の `api.ts:49–50` は `/session` で始まる全経路を失効イベントから除いていた。このため別タブ復旧の直後、旧タブが保存操作より先に復旧ダイアログの `/session/recover` を実行すると、CSRF専用403も局所エラーになり、画面内の全体再読込案内へ移らない経路があった。サーバーは正常に拒否するため情報漏えい・認証突破ではない。コード経路として指摘し、主担当へ修正を依頼した。
- **追加経路の修正確認:** 現行条件は `(401 && !session経路) || (403 && 専用ヘッダーtrue)` に分離され、復旧操作のCSRF専用403も全体へ通知する。`Recovery.tsx` は失効通知で発行済み・入力中の合言葉を消去して閉じ、`onClose` で古いエラー・成功メッセージも消す。通常の復旧コード不一致401はダイアログ内に留める。
- **追加経路の試験証拠:** 「別タブで引き継いだ後に古い引き継ぎ画面からも復帰できる」が実サーバーで合格。別タブでCookieを更新し、旧タブの復旧操作→ダイアログが閉じる→全体再読込→再度開いた画面に古い警告なし→誤コードを局所表示→正しいコードで復旧成功、を確認する。これは主担当の実行結果と試験コードを独立に照合した記録であり、レビュー担当が同じ15試験を再実行した記録ではない。
- **試行制限の確認:** 追加試験の初回は先行試験と同じ接続元の復旧5回/分枠を共有し、誤コードのエラーを期待した箇所で「1分待って」の制限応答になった。[初回記録](../artifacts/browser-tests-recovery-rate-limit.json)は14成功・1失敗として保持。制限を緩めず、追加試験前に61秒の冷却を設けた再実行で15成功。`recoveries_per_minute=5` と共通rate処理が維持されていることをソースで確認した。
- **範囲の限界:** 実期限の経過は時計差替えAPI試験、ブラウザー操作は復旧によるサーバー実失効で検証した。30日待機や端末休止からの実時間復帰、全画面の同時通信競合を網羅したものではない。ページ全再読込後は `sessionOpened` が初期化されるため、記録のない新規利用とCookie消失の区別はしない。元の記録を開くには保存した合言葉を使う。

### SEC-04 — 訂正版CSVの同一イベントが重複レコードになる

- **重大度:** 低（分析データの版管理）。固定サンプルの同一内容を繰り返す取込では重複しない。
- **状態:** 氏名訂正による重複は修正確認済み。元イベントIDがない場合の識別限界は残る。
- **箇所:** [analyze_samples.py:119](../scripts/analyze_samples.py)、[test_samples.py](../scripts/test_samples.py)。
- **修正前の根拠:** レコード識別子は保持対象列だけでなく、CSVの全原文行をHMACした値だった。
- **修正前の再現:** 同じuser・特典・時刻を持つ合成CSVを取り込み、保存しない `username` 列のみ変更して再取込した。保存件数が1件から2件になった。
- **修正前の影響:** 訂正ファイルを追加入力すると、実際のイベント増加と版更新を区別できず件数が増えた。ただし氏名等の原文が出力DBへ保存されるわけではない。
- **修正:** 識別子を、種別のHMAC領域＋user・subject・整形済み日時・スタンプの周回/名称または特典のprize_nameから作る自然キーに変更。原文行のHMACは同一ファイル内の完全一致行カウントにのみ使用する。標準出力DBを `data/analytics-v2.db` とし、旧方式のDBへ標準操作で追記しない。
- **確認:** 氏名と日時の区切り文字だけ訂正して再取込する追加試験で、保存件数1件・already_present 1件を確認。`scripts/test_samples.py` の全5試験をレビュー担当が独立再実行し、5件合格。
- **残る制約:** 同じ自然キーを持つ別イベントは区別できず統合される。逆に対象・時刻・周回等のキー列自体の訂正は別レコードとなる。アンケートは種別ごとに同一利用者を1件扱いとする。旧DBを明示的に指定した場合の自動移行・混在検出はないため、v2 DBへの新規取込を用いる。イベントID付きの定期運用や訂正・削除の同期を提供するときは、別途版管理・移行・失敗復旧の設計と試験が必要。

SEC-01〜04は追加の復旧経路を含め、具体的な修正・試験範囲で確認を終えた。自然キー識別限界、実時間待機・全競合条件、公開運用への拡張は未確認条件として引き継ぐ。15成功の最新記録に加え、14成功時点の記録と試行制限で失敗した記録も保持する。

検証スクリプトの補足（更新）: 先行版は任意のOSErrorによる書込み失敗を `rootfs_readonly` としていたため、権限不足とEROFSを区別できなかった。現行版は実験を `rootfs_write_denied`、`docker inspect` の `HostConfig.ReadonlyRootfs` を `rootfs_readonly` と分離し、両方を合格条件にした。ソースと保存JSONで両方trueを確認。書込み実験単独ではread-onlyを証明しない限界は残るが、実効設定の確認が自動化され、先行の追加検査提案は対応済み。
