# 開発リビジョンと改善履歴

単なる上書きで終わらせず、Gitコミットと本台帳で変更理由・試験・評価点を追跡する。開始前に存在したのは設計書とタスク計画で、アプリ実装はなかった。過去にコミットされていなかった変更の履歴を捏造せず、本台帳導入時点から保存する。

| リビジョン | 変更内容 | 判断理由 | 検証・評価 |
|---|---|---|---|
| R00 | 要件・API契約・評価基準・運用方針を固定 | 2つの再訪戦略、ローカル制約、20評価項目を実装の基準にする | 実装開始時 0/100。文書の存在と対応確認 |
| R01 | サンプルの品質確認と仮名化取込 | 提供データを元ファイル不変・個人情報非表示で活用する | 5ファイル、再取込不変、4試験成功。Q18により5/100（+5） |

R01では試験中にSQLite接続の未解放を検知し、明示的な終了処理へ修正。修正後4試験が通過した。点数は合格確認後に加算しており、不具合発見前の未検証状態を高得点として記録していない。

## 発表での追跡方法

- `git log --oneline` で変更順を確認。
- `git show <commit>` でその変更の差分を確認。
- 各段階の評価は docs/EVALUATION.md、試験証拠は artifacts/ を参照。
- 仕様変更は設計書も同時に更新する。未検証・失敗・未解決を履歴から消さない。
